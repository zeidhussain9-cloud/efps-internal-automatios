# EFPS CRM UI Dashboard — Project Instructions

## 1. Project Scope

This project is the operational development context for the **EFPS CRM UI Dashboard** and its supporting production CRM architecture.

The work is organized around **task-specific agents/workstreams**, not a single unrestricted agent. Agents may be assigned to focused responsibilities such as:

- CRM UI/dashboard implementation and UX hardening
- backend/API and reconciliation logic
- Supabase database, migrations, cron and Edge Functions
- WhatsApp/WhAPI webhook ingestion and reconciliation
- deterministic lead classification and status automation
- AI analysis and AI-run auditing when explicitly enabled
- inventory ingestion, reconciliation and UI
- authentication, privacy, safety, auditability and operator controls
- testing, browser regression and release verification
- production deployment and infrastructure verification
- documentation and repository-state reconciliation

Agents must stay within the scope of the task assigned to them and reuse the existing authoritative CRM architecture. Do not create duplicate or speculative data flows when an existing production path already provides the required behavior.

## 5. Current Verified Architecture Baseline

The current project baseline is:

- Webhook reconciliation is active.
- Inventory reconciliation is active.
- Deterministic CRM classification is active on its own scheduler.
- Deterministic classification does **not** call AI.
- The AI scheduler is intentionally paused; its implementation may remain installed, but there is no active recurring AI scheduler trigger.
- Pending conversations remain attached to the same classification record while new messages accumulate.
- Webhook evidence is retained in `crm_webhook_events`.
- Conversation evidence is retained in `crm_messages`.
- Deterministic qualification requires both customer-originated intent and property/requirement evidence.
- Outbound property/listing messages alone do not qualify a contact.
- Deterministic decisions must be auditable with rule version, reason/signals and supporting evidence IDs.
- Deterministically qualified leads use `auto_qualified=true` and the UI provenance label `AUTO QUALIFIED`.
- `Property Listing Sent` is historical/legacy data and is not generated by the deterministic engine.
- Existing operator-confirmed exclusions must remain protected.
- Lead names should use authoritative stored sender/display-name evidence when available; do not infer names from phone numbers or arbitrary message text.

The exact live counts and deployment identifiers are maintained in the current verified project documentation and must be rechecked before making a new “current” production claim.

## 6. Working Rules for Every Change

For every requested implementation or hardening task:

1. Check the current repository implementation.
2. Check relevant project context and prior decisions.
3. Trace the existing backend/data flow.
4. Verify the relevant live database/runtime state when applicable.
5. Implement first on `crm-ui-dashboard`.
6. Test the change using the appropriate repository, database and/or browser tests.
7. Update affected documentation so it describes the implementation actually verified.
8. Deploy when the task is production-impacting.
9. Verify the Render/live runtime when applicable.
10. Reconcile the verified repository tree into `main`.
11. Confirm `tree(main) == tree(crm-ui-dashboard)`.
12. Report evidence, not assumptions.

Do not report a feature as complete merely because code was written.

## 7. Source-of-Truth Order

When evidence conflicts, use this order:

1. Repository code and committed migration/function definitions
2. Live Supabase/database state
3. Automated tests and CI
4. Render deployment state
5. Browser/production verification
6. Project documentation

Documentation must reflect verified implementation rather than override it.

## 8. Agent Ownership Model

### CRM UI Agent
Owns dashboard pages, lead cards, status presentation, inventory UI, spacing, sorting, filters, menus, buttons, accessibility and browser UX.

### CRM Backend Agent
Owns APIs, repositories, reconciliation logic, promotion logic, status persistence and server-side behavior.

### Supabase Agent
Owns migrations, SQL, Edge Functions, cron jobs, database constraints, indexes, query performance and live database verification.

### Webhook/Reconciliation Agent
Owns WhAPI/WhatsApp event ingestion, webhook persistence, reconciliation, idempotency and message-to-contact/lead linkage.

### Classification Agent
Owns deterministic classification rules, evidence handling, reevaluation, audit provenance and scheduler behavior. It must not introduce AI into the deterministic path.

### AI Agent
Owns AI analysis only when explicitly enabled or requested. It must respect the current scheduler state and must not silently reactivate paused AI execution.

### Inventory Agent
Owns inventory synchronization, sheet reconciliation, image/data availability and inventory dashboard behavior.

### Security/Operations Agent
Owns authentication, privacy, safety controls, operator controls, archive/restore, export controls, auditability and failure handling.

### QA/Release Agent
Owns unit/integration tests, browser regression, CI verification, release gates and final evidence collection.

### Documentation Agent
Owns current-state documentation, handoff documentation, implementation specifications and removal/labelling of stale nonhistorical claims.

### Deployment Agent
Owns Render deployment verification, runtime health checks and production release evidence.

Agents may collaborate, but each change must have a clear primary owner and must preserve the boundaries above.
